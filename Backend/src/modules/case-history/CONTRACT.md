# WF05 case history contract (pinned at e8ccff8)

**Entry and scope.** The existing `/cases/:caseId/timeline` reads `TimelineEvent` without the case access gate; `TimeEntry` is separate, while client publication reads approved snapshots and updates. The new read endpoint must use `assertInternalCaseAccess` before querying a case and must not reuse raw audit descriptions for a customer DTO. No production defect has been verified in a live environment.

**Internal projection.** One item per stable `timeline:<id>` or `time:<id>` reference; skip a `TIME_LOGGED` audit item when it points to an included TimeEntry. Sort by occurrence time and source key for stable cursor pagination. Time totals sum only actual, exactly attributed `TimeEntry.minutes`; no inferred review duration and no cross-case matter-only allocation. Source authors, timestamps, and rows are read only.

**Customer eligibility matrix.** Level 1 (Rövid állapot): a published `ClientMatterPublicationRevision` can supply safe status, next action and target date. Level 2 (Mérföldkövek): level 1 plus published milestone snapshot, published `ClientSafeUpdate`, and approved/delivered document publication metadata. Level 3 (Részletes ügytörténet): level 2 plus separately reviewed customer-safe work text and allowed time facts, if ever durably approved. Raw `TimelineEvent` payload/description, `TimeEntry` description/rate/user, mailbox, review rationale, prompts, token maps and unknown categories are private at every level. An explicit item exclusion would override all levels. Existing grants and publication status are necessary at every level. The current code does not implement a durable policy, so no level is effective by default and this slice adds no customer disclosure.

**Persistence decision.** `ClientMatterPublication` has a versioned published revision and a milestone draft JSON, but neither represents a case/client history policy or per-item editable overlay. `ClientSafeUpdate` is a published item, not a policy; `ClientPortalGrant.participantRole=CLIENT_OWNER` denotes a portal participant, not a selected client-side case owner. No semantically valid policy/overlay/owner store was found. Do not put these in `SystemSetting`, browser storage, or the milestone JSON. Additive schema approval is needed for `(caseId, clientId, level, ownerOrganizationPersonId?, revision, updatedById, updatedAt)` plus a separate `(policyId, sourceType, sourceId, excluded, customerText?, revision, updatedById, updatedAt)` overlay with unique source reference. Validate owner membership against the case client and revoke/reselect when that client changes. Backfill must leave all existing cases without a policy. Publishing requires an explicit authorized save and review; no retroactive disclosure.

**Integration manifest.** In `Backend/src/index.ts`, import `{ caseHistoryReadRouter }` from `./modules/case-history/read.routes` and mount `app.use('/api/v1/case-history', caseHistoryReadRouter)`. In the WF01 Case Workspace host, import `{ CaseHistoryPanel }` from `@/components/cases/word-workflow/history/CaseHistoryPanel` and render with the authoritative `{ caseId, clientId }` props. The read route authenticates and checks internal case scope; it does not accept a customer caller. After approved policy persistence, make one server customer-history service call `projectCustomerHistory` only from validated publication rows, then consume its identical DTO in `Backend/src/routes/clientPortal.ts` `/matters/:publicationId` (after `resolveActiveCustomerGrant`) and #444 `Backend/src/modules/work-reports/service.ts` `buildCaseWorkReport`. Its current `resolveWorkReportOwner` selection remains report-only until durable case ownership exists. Do not reuse `TimeEntry.description` or internal audit payload for either customer consumer. No file in those integration surfaces is edited by WF05.
